# CyberTools Intelligence Execution Plan

This roadmap governs the staged evolution of CyberTools from a LibreChat deployment into a safe agentic platform.

## Non-negotiable safety rules

- Production is never changed directly; every stage uses a dedicated branch and pull request.
- Every stage must have a documented rollback.
- Desktop access is deny-by-default and root-scoped.
- Read access ships before write access; command execution is a later, separately approved capability.
- No agent may modify production code, prompts, or skills without evaluation, review, and promotion through staging.
- Secrets remain in environment variables and are never committed.

## Stage gates

### Gate 1 — Bidi and capability recommendations

Status: completed and deployed.

Deliverables:
- Mixed Arabic/English landing text uses automatic direction isolation.
- Smart Capability Advisor recommends accessible agents and active skills.
- Agent switching and skill application require explicit user action.

Acceptance:
- Railway deployment succeeds.
- Arabic UI no longer reverses English landing text.
- Recommendations do not change the send pipeline or consume model tokens.

### Gate 2 — Desktop Bridge foundation

Status: in progress.

Deliverables:
- Independent Tauri 2 desktop application under `apps/desktop-bridge`.
- User-selected allowed roots only.
- Read-only directory listing, text-file reading, and local filename search.
- Canonical path validation, symlink rejection, size limits, and audit log.
- No network listener, write, delete, shell, or process execution.

Acceptance:
- The desktop package builds independently.
- Railway build remains unaffected because the app is outside root workspaces.
- Attempts to escape an allowed root are rejected.

### Gate 3 — Secure pairing and local MCP adapter

Deliverables:
- One-time pairing code generated by the desktop app.
- Authenticated local WebSocket/MCP-compatible gateway bound to loopback by default.
- Per-operation approval policy and revocable sessions.
- Signed request envelope, replay protection, and complete audit trail.

Acceptance:
- No remote access before pairing.
- Roots remain authoritative on the desktop side.
- Network requests cannot bypass local approval rules.

### Gate 4 — Multi-layer memory and run ledger

Deliverables:
- Working, episodic, semantic, and procedural memory separation.
- Agent run ledger with intent, selected agent/skills, tool calls, result, latency, cost, and feedback.
- Retrieval filters by user, project, permission, recency, and source.

Acceptance:
- No cross-user memory leakage.
- Memories can be viewed, corrected, exported, and deleted.
- Retrieval quality is measured against a fixed evaluation set.

### Gate 5 — Local/cloud model router

Deliverables:
- Local intent classification, embeddings, summarization, and simple routing.
- Semantic result cache with state validation.
- Escalation policy to stronger cloud models only when needed.
- Provider health, quota, and fallback tracking.

Acceptance:
- Reduced cloud calls for routine tasks.
- No silent fallback to an unavailable or paid model.
- The selected provider/model is visible in traces.

### Gate 6 — Evaluation and learning sandbox

Deliverables:
- Offline evaluation datasets and replayable traces.
- Prompt/skill candidate generation from successful and failed runs.
- Sandbox benchmarks, canary comparison, and human approval.
- Staging promotion before production.

Acceptance:
- The system never self-modifies production directly.
- A candidate must outperform the active version without safety regression.
- Every promotion has an immutable rollback reference.

## Rollback policy

Each PR must identify:
- files and services changed;
- data migrations, if any;
- exact revert procedure;
- health checks and functional tests;
- the last known-good commit.
